# PM task and epic tools (COR-240)

The PM has `create_task`, `update_task`, `move_task`, `approve_task`, `delete_task` and `update_epic`. Definitions and confirmation policy live in `packages/contracts/src/pm-tools.ts`; runner registration and server dispatch both use them. Each tool accepts a `project` slug: required in Global sessions, optional in project sessions where it defaults to the session's project. Another project's slug selects that project. Confirmation cards retain the resolved slug so Confirm revalidates and acts on the same project. Calls use the existing task, transition, approval, deletion and epic services, with normal SSE updates and scheduler wakeups.

- `create_task` takes the create-task API fields and creates a Backlog task outside a plan. Description is a rich-text document (or null), criteria are strings, dependencies are task numbers, and `epicId` is an epic UUID.
- `update_task` takes `taskRef` and optional task PATCH fields, plus `paused`. Criterion lists replace the existing list; pass criterion IDs to preserve evidence. Main's D10 rule keeps Merged tasks immutable for every actor (`task_merged`); PM edits use the same service. PM changes to epicId are refused with task_epic_locked once a PR opens, preserving D27's review-mode lock. `canChangeType` in `packages/core/src/task.ts` is the one type-lock rule: a task's type is fixed once it is approved or awaiting merge, and it can't enter or leave `spike` or `design` once it has left Draft or Backlog. `patchTask` returns 409 task_type_locked for the PM, the human route and plans alike, so a design can't be retyped into approve_task's path to Ready to merge. Pausing a leased task is refused before any edit; use stop_run with human confirmation (preserving work). Pausing an unleased task sets its pause flag; resuming clears the pause and wakes scheduling.
- `move_task` takes `taskRef`, a typed `transition` using the board API's events, and an optional `reason`. `approve` places Draft/Backlog work onto the board; `accept`, `send_back`, `human_request_changes` and `resolve` retain the board's rules. D29's human-only transitions run on a confirmation card. Reasons are saved as task comments. Invalid transitions preserve the board API's structured error in the failed card.
- `approve_task` approves Human review through `merges.humanApprove`, including spikes, but refuses designs in favour of approve_design. The card binds the PR number and full head SHA; move_task cards include human_request_changes feedback. It and `delete_task` require confirmation. All three confirmation tools revalidate the live target on Confirm and retain human identity plus `viaPm` session/run attribution. No confirmation, no mutation; Cancel and repeated clicks use the existing durable lifecycle.
- `update_epic` takes `epicId`, optional `title`, `summary`, `reviewMode` and `dependsOn` (epic UUIDs). Summary maps to the epic's description. Metadata and dependencies commit together, so a rejected dependency graph rolls back both. Review mode is also available through the shared epic PATCH schema. `update_epic`, human PATCH and `propose_plan` revisions share `reviewModeLocked` from `epics.ts`. The PATCH service rejects mode changes with 409 once the epic or any task has opened a PR, or any task has merged (including deleted tasks). `patchEpic` and `PlanService.#propose` check under the epic row lock in their transactions. A locked-mode plan revision returns a clear tool error and rolls back the whole proposal, leaving the saved plan and epic unchanged. Unchanged modes, omitted modes and other metadata edits remain allowed; Draft plan revisions can change modes before any PR work exists.

Direct PM audit actors carry `sessionId` as well as `runId`. Task Activity now includes task mutation audit entries with a conversation link. Epic Activity reads `GET /api/epics/:id/history` (the audit detail's epicId), including title, summary, review-mode and dependency edits. Confirmed actions are labelled PM, confirmed by you.

All changed task fields, including title, priority and dependencies, now use the existing run-message service to notify a live Claude developer/reviewer. The message contains updated values and current criterion IDs. As before, runtimes that cannot accept live input (Codex), queued runs and unavailable runners receive a pinned task comment for get_task and subsequent turns; saving the edit does not depend on delivery.

`apps/server/src/pm-task-tools.test.ts` exercises the typed tools over the runner WebSocket and reads back task/epic history through the API. It covers every task status, board moves and errors, active-run messages, pause/resume, confirmation/cancellation/stale targets, project scope and atomic epic dependency rejection. `apps/server/src/plan.test.ts` also covers a locked-mode proposal after approval, task merge and session reopen, plus allowed Draft mode edits and unchanged/omitted modes. `CORRAL_PLAN_MODE_EVIDENCE` saves that regression’s HTTP/WebSocket records. Setting `CORRAL_PM_EVIDENCE_DIR` captures request/response records outside the repository for human review.

Inbox PM activity retains its project tag and conversation link after task deletion. `loadInbox` left-joins only live, non-soft-deleted tasks; absent targets return null taskId and taskRef so desktop and mobile do not load a missing task or offer task controls. `pm-actions.test.ts` covers confirmed deletion and captures API responses with `CORRAL_PM_DELETE_EVIDENCE`.
