# PM task and epic tools (COR-240)

The PM has `create_task`, `update_task`, `move_task`, `approve_task`, `delete_task` and `update_epic`. Definitions and confirmation policy live in `packages/contracts/src/pm-tools.ts`; runner registration and server dispatch both use them. Each tool is limited to the conversation's project. Calls use the existing task, transition, approval, deletion and epic services, with normal SSE updates and scheduler wakeups.

- `create_task` takes the create-task API fields and creates a Backlog task outside a plan. Description is a rich-text document (or null), criteria are strings, dependencies are task numbers, and `epicId` is an epic UUID.
- `update_task` takes `taskRef` and optional task PATCH fields, plus `paused`. Criterion lists replace the existing list; pass criterion IDs to preserve evidence. It can edit metadata in every status, including Merged as requested by COR-240; this does not reopen a merged task or change its shipped commit. Pausing an active task uses the existing stop-run service (preserving work); resuming clears the pause and wakes scheduling.
- `move_task` takes `taskRef`, a typed `transition` using the board API's events, and an optional `reason`. `approve` places Draft/Backlog work onto the board; `accept`, `send_back`, `human_request_changes` and `resolve` retain the board's rules. D27's human-only transitions run on a confirmation card. Reasons are saved as task comments. Invalid transitions preserve the board API's structured error in the failed card.
- `approve_task` approves Human review through `merges.humanApprove`, including spikes. It and `delete_task` require confirmation. All three confirmation tools revalidate the live target on Confirm and retain human identity plus `viaPm` session/run attribution. No confirmation, no mutation; Cancel and repeated clicks use the existing durable lifecycle.
- `update_epic` takes `epicId`, optional `title`, `summary`, `reviewMode` and `dependsOn` (epic UUIDs). Summary maps to the epic's description. Metadata and dependencies commit together, so a rejected dependency graph rolls back both. Review mode is also available through the shared epic PATCH schema.

Direct PM audit actors carry `sessionId` as well as `runId`. Task Activity now includes task mutation audit entries with a conversation link. Epic Activity reads `GET /api/epics/:id/history` (the audit detail's epicId), including title, summary, review-mode and dependency edits. Confirmed actions are labelled PM, confirmed by you.

All changed task fields, including title, priority and dependencies, now use the existing run-message service to notify a live Claude developer/reviewer. The message contains updated values and current criterion IDs. As before, runtimes that cannot accept live input (Codex), queued runs and unavailable runners receive a pinned task comment for get_task and subsequent turns; saving the edit does not depend on delivery.

`apps/server/src/pm-task-tools.test.ts` exercises the typed tools over the runner WebSocket and reads back task/epic history through the API. It covers every task status, board moves and errors, active-run messages, pause/resume, confirmation/cancellation/stale targets, project scope and atomic epic dependency rejection. Setting `CORRAL_PM_EVIDENCE_DIR` captures request/response records outside the repository for human review.
