# Request performance samples

Compose forwards both slow-warning thresholds from `.env` to the server, defaulting to 500 ms for requests and 200 ms for queries. An additive migration adds the complete performance table without changing existing migrations. The table lives in `packages/db/src/schema/performance.ts`, exported by the shared schema index.

The API timing middleware in `apps/server/src/performance.ts` measures handler time with the monotonic clock and sets `Server-Timing: total;dur=<milliseconds>, db;dur=<milliseconds>;desc="N queries"` on all API responses, including errors, health and SSE handshakes. This measures response preparation, not body transfer or the lifetime of a stream.

Ordinary requests enqueue one `api` sample with the same duration, HTTP status and registered route pattern. Unknown routes use `/api/*`; raw paths and query strings are never persisted or logged by this middleware. Health, client performance beacons, SSE responses and WebSocket upgrades are excluded from samples and slow warnings. The runner WebSocket lives outside `/api`.

`CORRAL_SLOW_REQUEST_MS` sets the slow-warning threshold (default 500 ms; nonnegative finite numbers accepted, invalid values fall back to 500). A request strictly above the threshold emits one warning containing method, pattern, status and duration.

One service-owned recorder flushes asynchronously every second, inserting batches of at most 1,000 samples. Requests never await database writes. Failed batches are logged and discarded so diagnostics do not retry indefinitely during an outage. Shutdown stops the timers and flushes pending samples before closing the database. A separate timer runs every minute and deletes all sample kinds older than seven days. The additive `perf_samples` migration includes an index on `(kind, created_at)` for later metrics queries.

Client performance uses `POST /api/perf/client`: a strict JSON envelope with a document `sessionId` (UUID) and 1–50 `{ name, metric, value }` records, at most 32 KiB. Invalid batches return 400 before any page sample is queued. Names must be known Nuxt page patterns; no concrete paths or query strings are accepted. The shared recorder stores these as `page` samples with nullable `metric` and `session_id` columns (existing API samples leave them null). Values use `duration_ms`; CLS is the exception, storing its unitless score.

The web client records initial navigation-to-`page:finish`, TTFB, DOM ready and window load from Navigation Timing, and each successful client navigation from the router guard to `page:finish`. Redirected/aborted navigations do not produce completed-page samples. `web-vitals` reports document LCP/INP/CLS snapshots as values change (latest value per metric within each batch), attributed to the landing page pattern and correlated by the document session UUID. Unsupported browser metrics or INP without an interaction are absent rather than invented as zero. Beacons flush every five seconds and on hiding/leaving the document, after the vitals' final callbacks. A refused beacon stays in a bounded 50-record queue for a later attempt. The prototype compile-time guard disables the plugin entirely.

Database calls made through the Drizzle client are timed at the driver query boundary using AsyncLocalStorage. Each API sample includes `queryCount` and `dbTimeMs`, including zero for requests without queries. Existing samples and non-API samples may leave these fields null. DB time sums completed query durations (including failures and driver waiting), so parallel queries can sum to more than handler time. Prepared executions and transaction queries are included; Postgres BEGIN/COMMIT/ROLLBACK statements pass through the query API, while PGlite manages transaction boundaries internally.

`CORRAL_SLOW_QUERY_MS` sets the individual query warning threshold (default 200 ms; nonnegative finite values accepted, invalid values fall back to 200). A query strictly above the threshold logs its SQL template and duration, never its bound parameter values. Request warnings add the registered route pattern, using the same fallback as API samples; background queries omit the route. SQL literals written directly in SQL remain part of the template, so application data should always use bound parameters. Sample flushes and pruning normally run outside request context and are not attributed to requests.

`GET /api/perf/summary?window=1h|24h|7d` (default 24h) aggregates samples for Settings → Performance: API routes and `navigation` page samples with Postgres `percentile_cont`, sorted by p95 descending, and the overall p75 of LCP/INP/CLS. Vitals use only the latest value per document session and metric, because each document reports growing snapshots. Route names carry no HTTP method, so methods on one pattern share a row. `slowThresholdMs` is `CORRAL_SLOW_REQUEST_MS` and applies to both routes and pages; the good/poor vitals ratings live in `apps/web/app/utils/performance.ts`.
