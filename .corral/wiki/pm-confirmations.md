# PM confirmation cards

Confirm-required tool definitions are shared in `packages/contracts/src/pm-tools.ts` and included in `apps/runner/src/mcp.ts`. `confirmRequired` is server policy, not caller input. The orchestrator checks it before dispatching a PM tool, validates its inputs and target, and passes the proposal to `PmActions`. New tools supply preparation (validation and a one-line summary) and execution through the same lifecycle. `approve_plan` retains its separate D9 consent rule.

Confirmation can depend on the input: `confirmRequired` may be a function, and `act_on_inbox` needs a card unless its action is `clarify`. `requiresPmConfirmation(tool, input)` is the only check, so an unknown action falls on the side of the card. `PmDecisions` (`apps/server/src/pm-decisions.ts`) prepares and executes `act_on_inbox`, `approve_design` and `request_design_changes`. They take a ref from any project, because `list_inbox` spans projects, and the audit entry goes to the target task's project. Confirm compares the fresh summary with the stored one, so a summary that names what was agreed (`approve` names the PR head) refuses a target that moved on after the card was shown.

`clarify` is a direct tool: it runs through `PmTools.call` with the `pm.tool_called` audit, linked to its task. It can't use `resolve`, which is human-only, so it uses the PM's `answer` transition, which keeps the review-round and failed-run counters.

`delete_task`, `approve_task` and `move_task` use confirmation cards (see [PM task tools](pm-task-tools.md)). `delete_task` was the first confirm-required tool. Like every project-scoped PM tool, these tools accept a `project` slug: required globally, defaulting to the session's project otherwise. The resolved slug is saved in the pending action so Confirm uses the same project. Each tool validates its target in that project and uses the matching human service. Deletion refuses merged tasks. The human actor carries `viaPm` with the proposing session and run; confirmed actions appear in Inbox Activity with a link to that conversation, including when deletion removes a Backlog task outright.

A `plan_messages` row of kind `confirmation` is the durable pending-action record: its id is the action id; its session/run identify the proposal; `pending_action` holds tool, validated inputs, summary, target id, state, result and error. This additive JSONB column requires migration 0035. Reloading the conversation restores cards. SSE updates replace messages by id.

`POST /api/plan/sessions/:id/actions/:actionId` accepts `{decision: "confirm" | "cancel"}` for a human only. A conditional database update claims the pending action once before calling services, so retries and competing clicks cannot execute twice. Confirm revalidates inputs and live target state and binds execution to the original target id. Invalid actions become failed cards with a persistent error. Cancel never runs the tool. Terminal cards retain disabled buttons.

Decisions append an `action_result` conversation message without starting a PM turn. The next human message includes the saved confirmation results in its warm prompt (including earlier decisions, so a result racing a turn start cannot be lost); cold starts also read them from history. Audit entries `pm.action_proposed`, `pm.action_confirmed`, `pm.action_cancelled` and `pm.action_failed` retain the action id, session, proposing run, tool and inputs. Confirmation also records the human and result. Lifecycle audit entries survive hard task deletion. A server restart marks an interrupted execution failed, with an instruction to inspect Activity before proposing again; it never automatically repeats an action with potentially completed external effects.

`request_design_changes` accepts only the latest submitted design version, matching the Inbox feedback service. Preparation and Confirm both check this: a newer submission makes the saved card fail without applying feedback or moving the task. The human can request a new card for the newer version.

`delete_project`, `stop_run`, `stop_all` and `resume_all` use the same lifecycle. `PmAction.targetId` is what a card is bound to: the task, project or run id (`PreparedPmAction.taskId` is separate, for the audit entry). A project card therefore can't fire on a new project that reused its slug. Deleting the conversation's own project cascades away the session and its messages, so `resolve` writes the `pm.action_confirmed` entry with no project (it records the action's own project when that still exists, which is how a global session's entries get one), publishes no message events, and returns the card from memory.

## Direct PM tools

Tools that act without a card are defined in `pmDirectTools` in `packages/contracts/src/pm-tools.ts` and implemented in `apps/server/src/pm-tools.ts`, over the services behind the matching routes. Every call writes a `pm.tool_called` audit entry with a readable `detail.summary`, whether it read, changed, changed nothing or failed; the PM's agent actor carries `sessionId`. `loadInbox` shows all of these in Activity with a link to the conversation, as `PmActivityItem`s when no task is involved. The confirm lifecycle shows there too: proposed, confirmed, cancelled and failed. Refused calls reach the PM as `Corral refused this: <error body>`.

`list_runs`, `list_projects` and `get_run` cap what they return and add a `note`. `get_run`'s transcript is the end of the run as text, without reasoning or usage, never longer than `transcriptLimit` characters. `create_project` gives its repository check 100 s, under the runner's two-minute tool-call limit, so a project can't be created behind a call the PM saw time out. `message_run` prefixes the text with "From the PM:".

`resume_all` limit: no PM turn starts while Corral is stopped (`startPmRun`), and stopping ends PM turns, so the PM can't propose it after a stop. Only a card already waiting from before the stop can be confirmed.

COR-323 makes `set_update_hold` confirm-required, using the same durable lifecycle as `stop_all`. Its card warns that PM turns queue once running workers and merges drain. The human can lift either phase through **Lift** in the updating banner (DELETE /api/update-hold); this resets the finishing latch and dispatches queued turns. `clear_update_hold` stays direct for turns already able to run, but cannot rescue a queued turn. The prototype mock implements the same Lift endpoint and status event. `pm-tools.test.ts` covers proposal without mutation, human confirmation, a latched queued turn, and dispatch after human release.
