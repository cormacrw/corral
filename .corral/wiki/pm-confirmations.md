# PM confirmation cards

Confirm-required tool definitions are shared in `packages/contracts/src/pm-tools.ts` and included in `apps/runner/src/mcp.ts`. `confirmRequired` is server policy, not caller input. The orchestrator checks it before dispatching a PM tool, validates its inputs and target, and passes the proposal to `PmActions`. New tools supply preparation (validation and a one-line summary) and execution through the same lifecycle. `approve_plan` retains its separate D9 consent rule.

`delete_task` is the first confirm-required tool. It is scoped to the conversation's project and uses the existing human task-deletion service. It refuses merged tasks. The human actor carries `viaPm` with the proposing session and run; confirmed actions appear in Inbox Activity with a link to that conversation, including when deletion removes a Backlog task outright.

A `plan_messages` row of kind `confirmation` is the durable pending-action record: its id is the action id; its session/run identify the proposal; `pending_action` holds tool, validated inputs, summary, target id, state, result and error. This additive JSONB column requires migration 0035. Reloading the conversation restores cards. SSE updates replace messages by id.

`POST /api/plan/sessions/:id/actions/:actionId` accepts `{decision: "confirm" | "cancel"}` for a human only. A conditional database update claims the pending action once before calling services, so retries and competing clicks cannot execute twice. Confirm revalidates inputs and live target state and binds execution to the original target id. Invalid actions become failed cards with a persistent error. Cancel never runs the tool. Terminal cards retain disabled buttons.

Decisions append an `action_result` conversation message without starting a PM turn. The next human message includes the saved confirmation results in its warm prompt (including earlier decisions, so a result racing a turn start cannot be lost); cold starts also read them from history. Audit entries `pm.action_proposed`, `pm.action_confirmed`, `pm.action_cancelled` and `pm.action_failed` retain the action id, session, proposing run, tool and inputs. Confirmation also records the human and result. Lifecycle audit entries survive hard task deletion. A server restart marks an interrupted execution failed, with an instruction to inspect Activity before proposing again; it never automatically repeats an action with potentially completed external effects.
