# Stable page instances across selections

**Routing rule:** a page with a persistent part and a changing part uses a parent route and a child route, not a stable key on one large page. The parent holds what stays and renders `<NuxtPage>`; the child is what changes. A constant `definePageMeta` key is only for a page whose whole content is the selection (Plan session, task) or a child that keys its own panes (agent run).

Plan session and task pages set a constant `definePageMeta` key. Agent pages use nested routes instead: `pages/agents/[name].vue` holds the header, stats and runs list under Nuxt's default key, so changing the run keeps them while changing agent creates a new page. Its `<NuxtPage>` renders the transcript child `[name]/[[runId]].vue` with `useAgentRuns`' `view` as a prop. The child sets a constant `definePageMeta` key: its panes key themselves by the selected run, so reaching the auto-selected run by URL keeps its draft, and Nuxt's router plugin only updates the layout's route after a same-child navigation when that key is unchanged (without it the phone tab bar stays hidden after Back). On a phone the parent shows `MobileAgent` or the child, never both. Project routes retain Nuxt's default keys, so a project's tabs share one `pages/projects/[slug].vue` instance and another project gets a new one, with nothing carried over.

Inbox uses nested routes: `pages/inbox.vue` holds the list and task flyout under Nuxt's default key, so it stays mounted with its tab, search and list scroll, and `provideInboxView` (`composables/useInboxView.ts`) shares that with the children through inject, not props: the held list, the selection, Open thread, `moveToNext` and `deleteThread`. It also owns everything that must outlive one item: closing the flyout for own-pane items and setting the mobile header, because Suspense mounts the next child before it unmounts the last, so a child's cleanup would blank the new header. `pages/inbox/[itemId].vue` has Nuxt's default key, its path, so each item is a new instance and per-item state resets by remounting, with no watcher; query-only changes such as the dock's `?task=` keep the instance. Read the selection from the view in a child: a replaced child's `useRoute` is frozen on its old path, so a send finishing late could not tell the selection moved. `<NuxtPage>` stays rendered with nothing selected, and `index.vue` is empty on a phone, because the layout's route catches up on a child finishing: hiding it leaves the tab bar hidden after Back. On a phone the parent `v-show`s `InboxMobile` off while an item is open, so its scroll and search survive. Task-to-task clicks and auto-advance after an action go through `itemRoute`, which drops the task query: an item always opens with the flyout closed (COR-190 open question 7). An action's item can leave the list before its response arrives, because Resolved rows have their own ids; the held list (see [query-layer.md](query-layer.md#inbox)) keeps it selected through that gap, so an open flyout stays until the move. The next item opens at its top with no error or busy state left over. Reply text, composer attachments, retry destination and human checklist belong to the selected item; evidence is keyed by the selected task. Live refreshes of the same item preserve the reply draft. A send finishing for an older selection cannot clear the new reply or advance the new selection.

Selecting an Inbox item makes no `GET /api/inbox`, even when it is unread. `POST /api/plan/sessions/:id/read` publishes `plan.session` with `markedRead: true` and `POST /api/deployments/:id/read` publishes `deployment.updated` with `markedRead: true`. Those events skip Inbox invalidation in `queries/dependencies.ts` and patch the cached row with `inboxWithRead`. Reading never changes what's listed or the count (D11), and `inboxQuery` reapplies the read over any load that was in flight.

TaskDetail clears its editing fields, confirmation, attachments and loaded data and returns to its default tabs on task-ref changes, and ignores responses for previous tasks, including saves, status changes, resume, place, comments and delete. `applyTask` is the one place an action's response becomes `task`, because slug and number derive from it. DesignReview is keyed by task. PlanConversation clears its reply, attached task and composer attachments when the session changes; a one-tap answer finishing in the previous session cannot restore its draft into the new thread. Agent run selection clears the transcript and ignores an older request that finishes after the selection changes. On desktop and mobile the transcript scroller and `RunComposer` are keyed by run, so scroll, expanded steps and a mid-run draft stay with their run.

Settings uses nested routes: `pages/settings.vue` holds the section navigation, and Profile, Agents, Runners and Appearance own their content and queries. The index shows Profile on desktop and the section list on mobile; unknown single sections retain the shell with empty content. Only Agents and Runners observe the stale-on-mount CLI query, so opening either scans without a section watcher or stable page key.
